# 로봇 시뮬레이션 시스템 통합 작업리스트

2026-10-27 개정 1.0 · 구현 기준 [`main 61e55ba`](https://github.com/WannaSleep3254/mujoco-ros2-manipulation/tree/61e55ba7040910bb25758b6310e353f35ed92b6f)

로봇의 동작을 시뮬레이션하고 검증하는 환경을 만들기 위한 작업리스트입니다. 완료한 뷰어 개선과 실행 기능을 출발점으로, 남은 신뢰성 문제를 확인하고 구성 요소를 점진적으로 분리합니다. 새로운 레퍼런스의 제안은 기대 효과와 변경 규모를 함께 평가해 반영합니다.

## 개발 방향

- **구성 요소 교체:** 로봇 모델, 시뮬레이터, 모션 플래너, 제어 인터페이스와 뷰어를 각각 교체하거나 확장할 수 있도록 구성합니다.
- **설치 환경 반영:** 현장 설비의 설계 파일과 배치를 작업 환경에 반영합니다.
- **동작 검증:** 구성한 환경에서 계획, 실행 결과, 충돌과 실패 원인을 확인하고 기록합니다.

현재는 MuJoCo·ROS 2·MoveIt 2로 동작 검증 기능을 개발합니다. ROS 2는 익숙한 개발 스택과 센서 SDK 연계의 활용성을 고려한 현재 구현 수단입니다. Three.js는 유지하고 공통 형상·상태·센서 공급원을 확장합니다. FAIRINO FR5·FR10과 UR5e는 초기 테스트 기준이며, 기능이 안정되면 지원 로봇을 늘립니다.

비공개 QML 로컬뷰어의 설계 파일 처리와 별도 설비 공정의 개발 일정은 각각 관리합니다. 공통 좌표·자산·상태 규약은 필요에 따라 맞추되, 각 프로젝트의 작업 순서를 이 목록에 그대로 가져오지 않습니다.

### W01 취소 정리 진단

과거 비교 시연의 취소가 중첩 실행에 도달했지만 종료·정리 완료가 지연된 사례가 있습니다. 정확한 대기 위치는 아직 확정하지 않았습니다. 먼저 노드 해제, ROS 종료, 소유 launch 종료, 작업자 대기의 진행 시각과 필요 시 스레드 스택을 남깁니다. 검사 실패 뒤에도 진단 자료를 보존합니다.

- [ ] 취소·타임아웃·접촉 정지 조건을 구분한 재현 입력 보존
- [ ] 실패 경로의 console audit·작업 ID·정리 단계 기록 보존
- [ ] 정지 확인, 작업 종료, 프로세스 종료의 판정 분리
- [ ] 원인을 확인한 뒤 종료 순서나 자원 수명 수정

### W02와 W03 환경 여유와 추종 검증

과거 선택 경로가 기둥과 약 1.8 mm 떨어진 명목 상태로 검사를 통과한 뒤, 실행 상태에서 접촉해 네이티브 인터록이 정지한 사례가 있습니다. 작은 환경 여유와 추종 차이의 조합이 원인 후보이며, 각 기여도와 발생 빈도는 추가 확인이 필요합니다. 현재 팔 사이 30 mm 계획 기준을 설비와의 공통 여유로 해석하지 않습니다.

- [ ] 명목 경로·실제 경로·관절 오차·환경 최소 간격을 같은 실행에 연결
- [ ] 형상 근사·표본 간격·제어 추종의 영향을 나누어 확인
- [ ] 환경 여유 정책을 팔 사이 거리 정책과 구분해 정의
- [ ] 접촉·시계 감시와 최종 경로 검사를 유지한 수정 검증

### W04 작업과 실행 경계

명령의 목적, 실행 방식, 계획 전략을 구분합니다. 예를 들어 새로운 관절 목표와 장치 명령은 명령 종류이며, 새 계획·검토한 궤적 실행·향후 캐시·Servo는 실행 방식입니다. 현재 `coordinated`와 `departure_timing`은 계획 전략으로 유지합니다.

작은 단계로 MoveIt 요청 변환, 궤적 전송·취소, 상태 수신을 분리합니다. 교체 경계에는 관절 이름·순서·단위·좌표계·제어 모드·시계 영역·상태 신선도를 명시합니다. 현재 v1 명령, 호환 자동 실행 경로, 승인한 동일 궤적 실행, 모델·환경·정책·시작 상태 검사와 중복 전송 방지를 보존합니다. 새 기능이 필요할 때 규약을 확장하며 기존 사용자를 한 번에 새 API로 옮기지 않습니다.

### W05 표시 공급원과 분석

Three.js를 유지하고 Foxglove의 패널 역할 분리와 Rerun의 시간축 분석을 현재 화면에 맞게 반영합니다. 과거 기록 탐색, 계획 미리보기, 실시간 상태를 구분하며 기록 재생에서 로봇 명령이 발생하지 않도록 합니다.

- [ ] 요청·계획·실행·상태·이벤트의 연결과 시계 영역 표시
- [ ] 현재 geom ID 목록과 구분한 로봇·부품·공구 계층 규약
- [ ] 대표 이미지·프로파일·점군 중 필요한 입력 1종 선정
- [ ] 공급원·자산·좌표·단위·원천 시각·수신 나이·순번 검증
- [ ] 입력량 제한, 최신 상태 우선 처리, 유휴·탭 비활성·실패 복구 평가

센서 종류와 데이터량은 실제 사용할 입력에 맞춰 정합니다. 공통 형식에 출처 이름을 추가한 것만으로 센서나 다른 엔진의 연결 완료를 판정하지 않습니다.

### W06 설치 환경의 실행 연결

기존 STEP 변환과 미리보기에서 이어서 진행합니다. 대표 현장 자산의 단위·원점·설치 변환과 시각·충돌 형상을 대조하고, 실행용 환경의 모델 정체성을 고정합니다. 현재 보수적인 box 충돌 근사가 작업 경로를 과도하게 막는지 평가한 뒤 필요한 형상부터 개선합니다.

실행 환경 선택은 표시 모델 선택과 별도 동작으로 둡니다. 환경이 일치하지 않으면 실행을 막고, 같은 환경에서 계획·검토·승인·취소·접촉 정지를 확인합니다. 원본 설계와 파생 메시가 담긴 현장 자산은 로컬에서 관리합니다.

### W07 기본 작업 단위

현재 이동·접근·후퇴 시연에는 실제 물체 파지가 포함되지 않습니다. TCP와 공구, Pose/IK 목표, 파지 후보, 물체 상태를 먼저 정의합니다. 경로의 출발 시점을 고르는 후보를 파지 후보로 부르지 않습니다. 계획상의 물체 부착 상태와 물리적인 파지·미끄럼 검증도 구분합니다.

### W08 성능 실험

현재 요청별 계측으로 계획 서비스, 출발 탐색, 최종 검사, 예약 대기, 최초 이동과 정착 시간을 나누어 봅니다. 사용자 체감 지연을 평가할 때에는 브라우저 요청부터의 구간을 추가로 연결합니다. 사람의 계획 검토·승인 대기는 계산 지연과 별도로 기록합니다.

- [ ] 반복되는 구간과 계획 대기로 실제 멈춘 시간 확인
- [ ] 캐시 적중·실패·환경 변경·시작 상태 불일치 비교
- [ ] 캐시 조회 뒤 경로 재검증 비용 포함
- [ ] 다른 플래너를 같은 입력·계산 예산에서 비교
- [ ] 고정 회귀와 별도로 표본·반복·실패를 보존하고 중앙값·최댓값 제시
- [ ] 충분한 반복 수를 갖춘 비교에서 p95 제시. 작은 표본은 개별 결과로 확인

현재 1.975 → 1.537초는 [동일 입력의 오프라인 출발 탐색](search_optimization.md) 결과입니다. OMPL 자체나 요청부터 실행까지의 전체 지연 개선 수치로 사용하지 않습니다. 현재 검토 계획은 일회 승인용이며, 과거 저장 계획은 읽기 전용입니다. 이를 장기 궤적 캐시로 확장하려면 모델·환경·공구·정책·시작 상태와 전체 경로를 다시 검사해야 합니다.

## 기능별 반영과 문서 유지

각 작업은 완료 기준을 만족하는 작은 기능 브랜치에서 진행하고, `devel` 검증 후 `main`으로 승격합니다. 미해결 진단을 CI 재실행 성공으로 닫지 않으며, 기존 실패와 새 수정 결과를 함께 보존합니다. 한 번에 대규모 프레임워크 전환으로 묶지 않습니다.

기능 변경 뒤에는 해당 사용 문서, 상태 표, 관련 리포트를 갱신합니다. 소개 페이지는 간략하게 유지하고 상세 내용은 방향성·검증 리포트에서 연결합니다. README는 사용자가 직접 편집하므로 별도 검토 요청이 있을 때 다룹니다.
