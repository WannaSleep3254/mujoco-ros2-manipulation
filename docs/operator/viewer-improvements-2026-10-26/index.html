Overview

상태 갱신과 화면 렌더링의 분리

기존 서버 JPEG 방식에 로컬 WebGL 표시를 추가했습니다. 브라우저는 준비된 형상과 관절 자세를 받아 장면을 그리고, 수신 주기와 별개로 카메라를 조작합니다. 물리 계산과 로봇 명령은 기존 실행 계층이 담당합니다.

이번 비교의 결론: 정지 장면에서 WebGL은 약 60 fps로 렌더링했지만 수신 자세 적용은 약 4회/s였습니다. HTTP 응답 본문량과 서버 합산 RSS는 낮았고, 평가 서버 프로세스 CPU 합계는 비슷한 수준이었습니다.

이 페이지는 2026-10-22 뷰어 개발 방향성의 후속 기록입니다. 당시 JPEG 구성과 미측정 항목은 과거 기록으로 보존합니다.

01 / Current design decision

Three.js를 유지하고 확장하는 이유

2026-10-26 설계 판단 현재 Three.js 표시부와 조작 화면을 유지하면서, 여러 시뮬레이터·로봇·센서의 데이터를 연결하는 부분을 단계적으로 분리하는 방향을 채택합니다.

  • 프로젝트의 조작 흐름을 이어갑니다. 작업환경 확인, 목표 입력, 계획·실행·취소와 결과 조회를 기존 화면에서 제공합니다. 표시부를 확장하면서 이 흐름과 기존 검사를 함께 유지합니다.
  • 표시와 계산을 나누어 발전시킵니다. 브라우저는 형상과 자세를 표시하고, 물리 계산과 로봇 명령은 백엔드가 담당합니다. 카메라는 새 상태가 도착하는 주기와 별개로 움직입니다.
  • 구성 요소를 교체하려는 목표에 맞춥니다. 모델 식별자, 좌표계, 단위, 시간과 상태 순번을 공통으로 정리하고 MuJoCo·기록 연결부를 분리했습니다. 실제 공급원과 데이터 종류를 늘리는 것이 다음 과제입니다. Three.js가 이미 여러 엔진을 지원한다는 뜻은 아닙니다.
  • 현재 확인한 표시 개선을 활용합니다. 정지 장면에서 약 60 fps 렌더링과 약 4회/s 새 자세 적용을 관측했습니다. 이 둘을 구분하면서 이동 중 부하와 입력 지연을 추가로 측정하고, 실제 요구에 따라 표시 기술을 다시 평가합니다.

판단의 범위: 기존 기능과 프로젝트 목표를 바탕으로 한 개발 선택입니다. Qt·Foxglove·Rerun과 같은 조건으로 성능이나 개발 비용을 비교한 결과는 아닙니다. MuJoCo 연결부는 MJCF와 MuJoCo 기구학 계산을 사용하고, 별도 기록 연결부는 이미 계산된 형상·자세를 읽습니다. 다른 실제 시뮬레이터·실물 로봇·센서 연결은 후속 개발 범위입니다.

기존 조작·실행 경로와 현재 표시 구조: 고정된 구현 근거 · 최초 대안 검토: 10/22 뷰어 개발 방향성

02 / Implementation

이미지 수신에서 로컬 장면 표시로

도식 1. 두 표시 경로

서버 JPEGROS 관절 상태 → 서버 MuJoCo FK·EGL 렌더 → JPEG → 브라우저 이미지
로컬 WebGL형상 자산 초기 수신 + 서버 CPU FK 자세 수신 → 브라우저 3D 렌더·자유 카메라

WebGL은 같은 자세를 여러 화면 프레임에 재사용합니다. 자세 적용률은 새 sequence의 수신 데이터를 적용한 횟수이며, 이 정지 실험에서 로봇 자세가 바뀌었다는 뜻은 아닙니다. 화면 렌더링 속도의 증가가 물리·제어 주기나 모션 계획 속도의 증가를 뜻하지는 않습니다. JPEG는 대체 표시 방식으로 유지합니다.

03 / Measured display behavior

정지 장면의 표시·전송·서버 부하

같은 홈 자세에서 방식별 15초 구간 3개, 총 45초를 관측했습니다. 전환·초기화 구간을 제외하고 준비된 상태에서 측정했습니다. 브라우저는 1280 × 720, DPR 1이며 JPEG 원본은 960 × 640, WebGL 캔버스는 621 × 414입니다. 동일 해상도 비교는 아닙니다.

HTTP 값은 실제 브라우저 GET의 응답 본문만 집계했습니다. 헤더·전송 계층 비용·계측 probe는 제외했으며, WebGL 초기 형상 자산 약 3.42 MB도 정상 표시 구간에 포함되지 않습니다. kB·MB는 1000 기준입니다.

CPU·RSS는 콘솔과 자손 프로세스의 합계로 브라우저 CPU·GPU를 제외합니다. CPU는 경계를 넘는 구간을 제외한 약 14.5초/창을 사용했습니다. 자세한 표본·분류·수치는 표시 성능 측정 리포트에서 확인합니다.

04 / Camera controls

확대·축소·감도 조절

조작 화면과 시연 화면에 확대·축소·기본 시점 버튼을 추가했습니다. 기존 휠·핀치 줌과 함께 사용할 수 있습니다. 조작 감도를 펼치면 회전·줌·이동을 각각 0.25~3배로 조절합니다.

  • 버튼 줌은 현재 바라보는 방향과 중심을 유지하며, 기존 카메라 거리 제한을 따릅니다. 기본 시점은 현재 모델을 다시 맞춥니다.
  • 감도는 조작·시연 화면에 함께 적용하고 같은 페이지의 모델·장면 전환에서 유지합니다. 새로고침하면 기본 1배로 돌아갑니다.
  • 서버 이미지 방식에서는 확대·감도를 비활성화합니다. 이 버튼은 브라우저 카메라를 조절하며 로봇 명령을 보내지 않습니다.

읽기 전용 모델에서 확대·축소·복귀, 키보드 감도 조절, 시연 화면 동기화, FR10 모델 전환 후 설정 유지와 이미지 모드 비활성화를 브라우저에서 확인했습니다. 거리 제한과 오류·미준비 차단은 단위 검사로 확인했습니다. 실제 터치 장치와 조작 입력 지연은 별도로 측정하지 않았습니다.

Execution review & recovery

계획을 확인하고 실행까지 이어가는 화면

일반 관절 조작은 계획 생성 → 경로 미리보기 → 승인·실행 순서로 진행합니다. 미리보기 자체는 로봇에 명령을 보내지 않습니다. 시연은 별도로 선택한 비교 절차를 실행합니다.

  • 표시 대상 구분: 실시간 관절 상태, 실행 전 계획, 과거 기록과 모델 보기를 구분합니다. 표시 중인 모델과 실제 실행 대상도 따로 확인합니다.
  • 검토 정보: 계획 방식, 예정 궤적 시간(시뮬레이션 초), 최소 간격과 계획 시작 자세에서 목표까지의 관절 변화량을 한곳에 모읍니다. 느린 재생과 최소 간격 시점 이동으로 경로를 확인합니다. 원본 변화량은 rad로 보존하고 화면에서는 deg로 표시합니다. 경로 길이나 현재 실시간 자세와의 차이를 뜻하지 않습니다.
  • 재계획: 만료되거나 목표가 달라진 계획은 실행할 수 없습니다. 실시간 보기로 복귀해 같은 입력으로 새 계획을 요청할 수 있으며, 새 계획에도 다시 검토와 승인이 필요합니다.
  • 작업 이력: 계획과 승인 실행을 연결해 목표, 승인, 실행 결과를 따라갑니다. 원본 요청 식별자와 상세 자료는 함께 보존합니다.
  • 오류 복구: 상태·자세 조회에 시간 제한을 두고, 3D 표시 오류에는 명시적인 다시 열기와 서버 이미지 전환을 제공합니다. 표시 복구가 실행 명령을 다시 보내지는 않습니다.

실행 전 검사: 승인 시 시작 자세와 모델·환경을 다시 확인합니다. 계획 유효 시간은 60초이며 승인은 한 번만 사용할 수 있습니다. 표시한 최소 간격은 해당 계획의 검사 결과로, 실물 안전 기능이나 모든 환경의 회피 성능을 보증하지 않습니다.

검증: Python 619개, JavaScript 99개 검사와 독립 ROS 승인 검사 10개를 통과했습니다. 실제 브라우저에서 계획 만료·재계획·미리보기·승인 실행·연결 이력을 확인했습니다. 자세한 범위는 검증 기록에서 확인합니다.

P4 · 후속 확장준비된 모델·작업장면의 미리보기, 저장 궤적 재생과 실행 전 새 계획의 검토·승인을 구현했습니다.가져온 설비를 포함한 실제 회피 실행, Pose/IK·그리퍼·AMR 조작은 후속 범위입니다.

준비된 모델의 미리보기는 임의 로봇·설계파일을 바로 연결하는 기능과 구분합니다. 저장 궤적의 재생은 새 계획을 실행 전에 승인하는 기능과 구분합니다. 기존 문서의 본문은 10/22 당시의 판단과 계획으로 보존합니다.

06 / Proposed next steps

다음 확장과 재검토 조건

후속 개발안 공통 연결부를 작은 사례로 검증한 뒤 데이터 종류와 공급원을 늘립니다.

  1. 공통 형식의 확장: 구현한 형상·자세 형식에 직선 관절과 새로운 데이터 종류를 단계적으로 추가합니다. 표시부의 확대가 로봇 실행 권한을 추가하지 않도록 구분합니다.
  2. 장면 탐색과 대기 부하: 화면 맞춤과 개별 대상 탐색을 보완하고, 대기 중 렌더링과 조회를 줄입니다. 표시 프레임 분포와 장면 규모를 계측한 뒤 최적화 여부를 판단합니다.
  3. 센서·점군 확장: 자세와 별도의 전송 경로에서 데이터 크기와 대기열을 제한하고, 데이터 취득 시각의 좌표 변환과 오래된 데이터 처리 규칙을 검증합니다. 임의 설계파일의 변환·가져오기도 별도 과제로 진행합니다.
  4. 관측·분석 도구 평가: ROS 센서·TF 관측이 주가 되면 Foxglove를, 시간축 기록 분석이 주가 되면 Rerun을 비교합니다. 원격 배포·라이선스와 실제 자료의 처리 성능을 확인하고, 실행·취소 경로와 구분해 연결합니다.

재검토 조건: 실제 이동·센서 자료에서 표시 지연이나 자원 사용이 요구 수준을 넘거나, 전용 표시 기능의 유지 비용이 커지면 다른 뷰어와 같은 조건으로 비교합니다. UI 프레임워크와 전송 방식의 변경도 각각 필요한 기능과 측정 결과를 근거로 결정합니다.

Scope & limitations

정지 장면 예비 비교의 한계

아래는 표 1의 원래 정지 장면 비교 범위입니다. 동일 GPU의 움직이는 기록 비교와 이번 기능 검증은 근거 목록에 별도로 연결했습니다.

  • 브라우저·GPU 부하, GPU 렌더 시간·메모리와 카메라 입력부터 표시까지의 지연은 측정하지 않았습니다.
  • 로봇 이동·계획 실행 중 부하, 원격 네트워크, 긴 시간의 안정성은 비교하지 않았습니다.
  • 정지 자세·서로 다른 해상도의 짧은 비교입니다. 모든 장면에서 전송량 감소나 자원 절감을 보장하지 않습니다.
