Overview / Measured result

캐시 적중 뒤에도 검증 비용은 유지

작은 공동 관절 목표 한 개에서 warm 캐시는 3회 모두 경로를 재사용했습니다. 새 계획 RPC는 생략했지만 출처 확인과 전체 경로 검사는 유지했습니다.

수신부터 plan_ready까지의 중앙값은 RRTConnect 캐시 off 0.631 s, RRT 캐시 off 0.608 s, RRTConnect cold 0.742 s, warm 0.572 s였습니다. 조건별 표본은 3개이며, 이 입력의 관측 결과를 다른 작업의 성능 순위로 일반화하지 않습니다.

현재 판단: 기본 RRTConnect와 캐시 off를 유지합니다. 이번 작은 표본에서는 반복 요청의 재사용 동작을 확인했지만, 기본 플래너나 캐시 정책을 바꿀 만큼 다양한 입력과 반복 수를 평가하지 않았습니다.

이 문서는 기존 모션 계획 방향성과 시스템 개발 방향의 W08 후속 측정입니다. 기존 고정 성능 리포트와 fixed_motion_v1 시험은 변경하지 않았습니다.

01 / Implementation

플래너 선택과 검증된 경로 재사용

기본 동작
기존 4개 필드의 관절 명령과 RRTConnect·캐시 off를 유지했습니다. 내부 설정과 CLI에서 두 플래너를 명시적으로 선택할 수 있습니다.
캐시 대상
전체 관절을 포함하는 coordinated 관절 계획의 plan-only·자동 실행 요청만 대상으로 합니다. Pose, 출발 지연 탐색과 승인 실행은 캐시 조회·저장 대상에서 제외합니다.
일치 조건
소스, 모델, 환경, 도구 없음, 정책, 플래너의 6개 신원과 전체 관절의 목표·시작 상태를 대조합니다. 실제 Planning Scene의 객체·ACM·변환, native 소스·바이너리 신원도 확인합니다.

도식 1. 캐시 후보의 검증 절차

조회·출처 확인원본 경로의 신원·TTL·전체 상태
→
경로 재검증시작점·첫 구간 동역학·native·MoveIt
→
새 검토 발급현재 환경·상태 재확인과 새 토큰
  • 캐시 경로 자체가 거부된 경우에만 항목을 제거하고 남은 동일 계산 예산에서 새 계획을 시도합니다. 취소, 예산 초과, 신원 오류와 통신 오류는 실패로 전달합니다.
  • 실험의 시작 허용 오차는 0.0001 rad입니다. 원천 피드백을 과거 상태로 덮어쓰지 않고 반환 사본의 첫 위치만 현재 상태에 맞춥니다. 바뀐 첫 구간의 연속 위치·속도·가속도 한계와 전체 경로를 다시 검사합니다.
  • 재사용은 원래 저장된 시작점·TTL을 갱신하지 않습니다. 승인 시에는 검토한 동일 경로를 재계획 없이 실행하고 기존 승인·상태·환경·전체 경로 검사를 유지합니다.

신원 확인의 바이너리 범위는 native evaluator 소스·helper 바이너리·엔진 버전입니다. 모든 OS·ROS 공유 라이브러리의 로드 바이트를 증명하는 기능은 아닙니다.

02 / Evaluation conditions

동일한 입력과 종료점

표 1. 고정 비교 조건
항목조건
작업 환경·입력그리퍼 없는 FR5·UR5e 공동 환경입니다. 정의한 home에서 각 팔 첫 관절을 +0.12 rad로 계획하고 나머지 목표는 유지합니다. 실제 시작 상태는 매번 관측했으며 명목 home과의 차이를 기록했습니다.
조건·반복RRTConnect off, RRT off, RRTConnect cold, RRTConnect warm을 각 3회 측정했습니다. warm-fill 준비와 기능 사례는 성능 표본에 포함하지 않았습니다.
계획 설정coordinated, 외부 공간 후보 최대 1개, 목표 허용 오차 0.003 rad입니다. 각 MoveIt 요청의 num_planning_attempts는 3입니다. 후보 1개와 내부 시도 수를 구분합니다.
계산 예산5.0 s 협력 예산을 사용했습니다. 실험용 review_in_compute_budget=True로 모든 조건에서 마지막 검토 환경 조회까지 포함했습니다. 프로세스를 5초에 강제 종료하는 제한은 아닙니다.
주 지표서버 단조 시계의 요청 수신부터 plan_ready 이벤트까지입니다. 마지막 환경 확인과 새 검토 발급을 통과한 공통 종료점을 사용합니다.
환경Intel Core i7-13700 · 논리 CPU 24개 · 약 33.4 GB RAM · Ubuntu 22.04.5 LTS · Python 3.10.12 · ROS 2 Humble · Cyclone DDS · native MuJoCo 3.12.0

계산 시간과 계획 RPC는 보조 지표입니다. 서버 준비, warm-fill과 물리 실행 시간은 위 주 지표와 별개입니다. p95는 조건마다 유효 표본 20개 이상이라는 기준을 충족하지 않아 게시하지 않습니다.

요청한 플래너와 실제 구성 근거

요청에는 RRTConnectkConfigDefault 또는 RRTkConfigDefault를 넣었습니다. 생성 설정과 실행 중 등록 파라미터의 타입을 대조했고, 최종 실행 로그에서 geometric::RRTConnect와 geometric::RRT를 사용하는 구성 메시지를 확인했습니다. GetMotionPlan 응답에는 선택된 플래너 ID 필드가 없어 이를 요청 값으로 채우지 않았습니다.

최종 로그의 타입 메시지는 RRTConnect 11개, RRT 3개입니다. 준비 이동도 포함하므로 이 수를 성능 12개 행의 실행 횟수와 동일시하지 않습니다.
