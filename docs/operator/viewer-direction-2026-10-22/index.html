접촉·시계 감시는 기존 네이티브/ROS 계층이 담당합니다. 표시용 렌더러는 물리를 적분하거나 제어 명령·시계를 발행하지 않습니다.

960 × 640표시용 원본 이미지 크기
최대 5 fps렌더러 설정 상한 · 실측 아님
250 msHTTP 상태 조회 예약 간격
프리셋 3개전체 · 정면 · 상단 카메라

JPEG 품질 설정은 88입니다. 250 ms는 약 4 Hz의 조회 예약 간격이며 응답 완료 주기나 실제 표시 FPS를 보장하지 않습니다. 위 설정은 물리·제어 주기와 별개입니다. [코드 1]

목표 입력·계획·실행과 요청의 진행·완료 표시를 녹화한 시연입니다. 실제 물체 파지는 포함하지 않습니다.

웹 조작 화면의 도입 목적은 다수의 터미널과 MuJoCo·RViz로 분산된 조작 흐름을 통합하는 것입니다.

02 / Alternatives & trade-offs

렌더링 대안과 트레이드 오프

대안은 UI 실행 환경과 3D 렌더링 위치의 두 축으로 비교합니다. 웹·데스크톱 UI 모두 클라이언트 렌더링과 원격 상태 수신을 구성할 수 있습니다. 비교표는 모델 재사용, 구현 범위, 배포와 운영 비용을 정성적으로 평가한 것이며, FPS·지연 순위는 별도 측정 대상입니다.

  • MuJoCo·RViz·추가 뷰어를 동시에 열면 중복 렌더링 부하도 포함해 측정해야 합니다.

서버와 사용자 PC를 분리할 때

  • 클라이언트 3D는 모델 자산과 상태를 보내고 사용자 PC가 표시합니다. 자산·기구학 일치가 주요 비교 항목입니다.
  • 이미지 전달 방식은 서버가 그린 프레임을 전송합니다. 영상 대역폭·지연이 주요 비교 항목입니다.
  • PC 대수만으로 결정하지 않습니다.

Qt 구성 검토

Qt/QML을 UI로 채택하더라도 3D 렌더링 경로는 별도로 선택해야 합니다.

  • 모듈 선택: Qt Quick 3D와 QOpenGLWidget 기반 렌더링은 구현 경로가 다릅니다.
  • 통합 비용: 선택한 모듈에 따라 모델 자산과 기존 렌더링 코드의 재사용·변환 범위를 함께 평가합니다.

공통 3D 상태 게이트웨이와 교체 어댑터는 제안 단계입니다. 카메라 조작과 로봇 목표 전송을 분리하고, 실행 요청에는 현재 요청 ID·단위·취소·결과 확인 규약을 적용하는 구조입니다.

P0 · 안정화

현재 기능·문제·비교 기준을 고정

  • 30 mm 거리 조건으로 거부되는 홈 복귀를 재현하고, 거부와 재계획 정책을 구분합니다. 뷰어의 오류 표시가 내부 실패를 가리지 않게 유지합니다.
  • 로컬 리포트 제공 경로와 정적 배포 경로의 불일치를 해소합니다. 로컬 시연 페이지의 404 응답을 고정 회귀 사례로 보존합니다.
  • 현재 JPEG 방식의 실제 FPS·표시 지연·CPU/GPU·물리 실시간 배율을 먼저 기록합니다. 렌더 설정 상한을 측정값으로 사용하지 않습니다.

공정한 비교를 위한 실행 조건
  • 같은 PC·OS·드라이버·전원 정책에서 뷰포트 픽셀 수와 DPR을 맞추고 앱/브라우저·모델·소스 커밋을 기록합니다.
  • 먼저 기록 상태 재생으로 렌더러만 비교한 뒤, 같은 ROS 시뮬레이션에 연결해 전체 영향을 확인합니다. 기록 재생 결과로 물리/제어 성능을 주장하지 않습니다.
  • 기본 비교는 뷰어 하나씩 실행합니다. MuJoCo·RViz까지 함께 띄운 실제 운영 조건은 별도 묶음으로 기록합니다.
  • 워밍업·반복 횟수·측정 구간과 사용 도구를 사전에 고정하고 원본을 남깁니다. 목표 FPS·허용 지연·자원 한계는 기준 측정 후 결정합니다.
  • 이상치·실패 실행을 임의 제외하지 않습니다. 로컬/원격, 캐시 유무, 센서/포인트클라우드 추가 여부를 섞어 평균내지 않습니다.

렌더러별 처리량, 원격 대역폭·반응성, 개발·배포 비용은 후속 비교 리포트의 평가 항목입니다. 현재 문서의 정성 비교와 구현 설정은 실측 결과와 구분됩니다.
